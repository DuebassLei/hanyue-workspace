## 2. 依赖关系与建议顺序

```
01 热榜规范  ──(独立)────────────────────────────► 可并行
02 提示词合并 ──(提供统一类型/正反向能力)──┐
03 分镜统一风格 ──(复用 02 的风格/正反向枚举)──┤──► 建议 02 先于 03
04 文章管理页  ──(独立)────────────────────────────► 可并行
```

| 优先级 | 项 | 理由 |
|---|---|---|
| P0 | 01 热榜规范 | 独立、收益最高（新增平台从"改代码"变"加脚本"）、是首页热榜接入的前置 |
| P0 | 04 文章管理 | 独立、纯前端为主、直接解决"不好管理"的痛点，风险最低 |
| P1 | 02 提示词合并 | 涉及数据迁移 + 全链路字段贯通，是 03 的能力基础，需先定数据模型 |
| P2 | 03 分镜风格 | 依赖 02 的风格枚举/正反向约定；改动面涉及并发与历史快照，最后做更稳 |

**可并行分组**：`01 + 04` 一组先做；`02` 单独一组；`03` 待 `02` 定稿后启动。

## 3. 跨项共用决策（✅ 已确认：全部按推荐项）

> 2026-11-19 用户拍板：**全部按推荐项执行**，并明确一条总原则——
> **配置类数据（热榜源注册、提示词/风格预设、分镜风格）全部为全局资源，由管理员统一维护；普通用户只读使用。**
> 文章稿件属于用户创作数据，不在"管理员维护"范畴（按现有所有权/工作区规则，见 04）。

| 决策点 | 影响项 | ✅ 最终决策（推荐项） | 落地要点 |
|---|---|---|---|
| D1 租户模型 | 01 / 02 / 04 | 热榜全局共享；提示词/风格合并后**全部全局、管理员维护** | `prompt_templates.owner_user_id` 改为可空且对新建管理员记录恒为 null（null=全局）；所有用户可读可用，仅管理员可增删改 |
| D2 正反向支持策略 | 02 / 03 | 供应商能力探测 `supportsNegativePrompt`，不支持时 UI 明示、服务端把负向词拼进 prompt 尾部 | 遵守 `docs/design.md:495`"不得静默声称参数生效" |
| D3 风格来源 | 02 / 03 | 抽出统一 `style_presets` Registry（风格枚举/后缀/参考图），提示词库与分镜都引用，管理员维护 | 避免第三套风格体系 |
| D4 文章状态机 | 04 | 复用 `publish_jobs.status` 展示真实发布状态，`content_items.status` 暂不引入新状态 | 现状稿件 status 恒为 draft，不引入独立状态机 |
| D5 "示例图"存储 | 02 | 复用 `assets` + 新增 `prompt_id` 可空列（或 `prompt_previews` 关联表） | 示例图落库、可跨会话预览 |

> D1 已落地：合并时"用户私有提示词"**并入全局**、由管理员接管（保留 `owner_user_id` 原值仅作来源追溯，不影响可见性）。各子文档末尾"待确认问题"均已按本节结论更新为**已定**。

## 5. 全局实施原则（沿用项目现有约定）

1. **单一真相源**：任务类型看 `manifest.yaml`（`apps/api/app/resources/scripts/manifest.yaml`）；平台清单、风格枚举都收敛到一处，禁止再出现"文档 11 平台、代码 22 平台"的漂移。
2. **不静默降级**：任一源/字段失败要明确记 `notes` 或在 UI 明示，不返回空数据冒充成功（延续 `services/hot_topics.py` 三条不变量）。
3. **快照可追溯**：凡是"当时用什么风格/提示词出图"，都要像 `characterSnapshot` 一样在入队时快照进 job payload，历史可复现。
4. **迁移幂等**：新增列同时改 ORM 模型 + `core/db.py` 的 `_ADDED_COLUMNS`；数据迁移可重复执行不重复写。
5. **无权限点不等于无权限**：稿件入口复用 `studio.use`；若引入精细授权，按 `docs/rbac.md:260-269` 同步测试。
6. **测试随之更新**：现有测试钉死了很多"旧行为"（如分镜风格资产被挤掉、内嵌负向句），设计变更需同步调整断言。
